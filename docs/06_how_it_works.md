# 06. 작동 원리 설명 노트 (발표·질의응답 대비)

> 과제 규정: **생성형 AI로 짠 코드라도 구현 내용과 작동 원리를 직접 설명할 수 있어야 함.**
> 이 문서는 "교수님이 물으면 이렇게 답한다" 수준으로 정리합니다. 코드를 바꾸면 여기도 같이 고치세요.

---

## 1. 전체 흐름 한 문단

웹캠 프레임 1장이 들어오면 **객체탐지 모델**이 손의 위치(박스)와 손 모양(클래스: one, fist, palm, like, dislike, peace)을 동시에 찾습니다.
그런데 한 장만 보면 손이 흔들리거나 순간적으로 다른 클래스로 잘못 나오므로, `gestures.py` 가 **여러 프레임을 모아서** 판단합니다:
최근 5프레임 다수결로 제스처를 안정화하고, 검지 위치는 커서로, "검지 → 주먹" 변화는 클릭으로, 손바닥 중심이 빠르게 옆으로 움직이면 스와이프로, 엄지를 일정 시간 유지하면 확인으로 바꿉니다.
이 명령들이 WebSocket 으로 브라우저에 전달되어 키오스크 화면이 움직입니다.

---

## 2. 사용 모델의 특징·작동 원리

### 2-1. 객체탐지란
이미지에서 **"무엇이(클래스) 어디에(박스)"** 있는지 찾는 문제. 분류(이미지 전체에 라벨 1개)와 달리 여러 물체의 위치까지 출력합니다.
우리 문제에서는 "손 모양" 자체를 클래스로 두어 **한 번의 추론으로 손 위치 + 손동작**을 같이 얻습니다.

### 2-2. YOLO 계열 공통 원리 (One-stage 탐지기)
- 이미지를 CNN 백본으로 특징맵으로 만들고(Backbone), 여러 크기의 특징을 섞은 뒤(Neck, FPN/PAN), 특징맵의 각 위치에서 박스와 클래스를 **한 번에** 예측(Head)
- 기존 YOLO(v8, 11 등)는 같은 물체에 박스가 여러 개 겹쳐 나오기 때문에 **NMS(Non-Maximum Suppression)** 후처리로 겹치는 박스 중 점수가 가장 높은 것만 남겼음

### 2-3. YOLO26 의 특징 (우리 주력 모델)
| 특징 | 설명 | 우리 서비스에 의미 |
|---|---|---|
| **NMS-free 엔드투엔드** | 학습 단계에서 물체 하나에 예측 하나가 대응되도록 배워서 NMS 후처리 없이 바로 결과 출력 | 후처리 시간이 사라져 지연이 안정적 → 실시간 커서에 유리 |
| **DFL 제거** | 박스 경계를 분포로 예측하던 Distribution Focal Loss 를 없애 헤드를 단순화 | CPU·ONNX 변환이 쉬워 노트북에서 돌리기 좋음 |
| **ProgLoss** | 학습 진행에 따라 손실 항목 비중을 조절 | 학습 안정성 |
| **STAL** | 작은 물체에도 정답 박스가 배정되도록 하는 라벨 할당 | 1~2m 떨어진 **작은 손**을 놓치지 않게 |
| **MuSGD** | SGD 에 대형 모델 학습에서 온 최적화 아이디어를 섞은 옵티마이저 | 빠르고 안정적인 수렴 |

모델 크기: n(nano) < s < m < l < x — 우리는 CPU 시연을 고려해 **n** 을 기본, **s** 와 비교.

### 2-4. RF-DETR 의 특징 (비교 모델)
- **DETR 계열 = 트랜스포머 탐지기**: 고정 개수의 "쿼리"가 각각 물체 하나를 맡아 박스·클래스를 예측. 학습 시 예측과 정답을 **헝가리안 매칭(1:1 매칭)** 으로 짝지어 손실 계산 → 구조적으로 **NMS 불필요**
- **DINOv2 백본**: 대규모 자기지도학습으로 사전학습된 ViT 를 백본으로 사용 → 적은 데이터로도 새 도메인에 잘 옮겨감
- **가중치 공유 NAS(신경망 구조 탐색)**: 한 번 학습한 네트워크에서 해상도·층 수 등을 바꾼 여러 하위 구조를 재학습 없이 평가해 정확도-속도 균형을 고를 수 있음
- 비교 포인트: **CNN(YOLO26) vs 트랜스포머(RF-DETR)** — 같은 데이터에서 mAP, 지연시간, 작은 손 탐지 차이

### 2-5. 데이터 — HaGRID
- 3만 명 이상, 0.5~4m 거리, 다양한 배경·조명의 손동작 이미지. 손 박스 + 제스처 라벨이 이미 있음
- 주석 박스는 `[왼쪽위 x, 왼쪽위 y, 너비, 높이]` (0~1) → YOLO 는 `[중심 x, 중심 y, 너비, 높이]` 라서 `prepare_hagrid.py` 의 `hagrid_to_yolo()` 가 변환
- `no_gesture` 박스(제스처가 아닌 손)는 기본적으로 제외, 옵션으로 클래스로 학습하면 "그냥 들고 있는 손" 오탐을 줄일 수 있음

### 2-6. 평가 지표
- **IoU**: 예측 박스와 정답 박스의 겹친 면적 / 합친 면적
- **AP**: 한 클래스의 정밀도-재현율 곡선 아래 면적. **mAP50** = IoU 0.5 기준 AP 의 클래스 평균, **mAP50-95** = IoU 0.5~0.95 (0.05 간격) 평균 → 박스를 얼마나 정확히 맞추는지까지 반영
- **지연시간(ms)·FPS**: 키오스크는 실시간이 중요 → 같은 이미지·같은 래퍼(`kiosk/detector.py`)로 측정해 공정 비교
- **명령 인식률 / 오발동률** (우리가 정의): 시나리오대로 동작했을 때 의도한 명령이 실행된 비율 / 하지 않은 명령이 실행된 비율 — 탐지 mAP 가 높아도 서비스가 잘 되는지는 별개라서 따로 측정

## 3. 코드별 설명

### `kiosk/detector.py` — 탐지기 래퍼
- YOLO / RF-DETR / mock 을 `detect(frame) -> [Detection]` 하나의 형식으로 통일 (어댑터 패턴)
- 좌표를 이미지 크기로 나눠 0~1 로 정규화 → 카메라 해상도가 바뀌어도 뒤쪽 로직 그대로
- torch 같은 무거운 라이브러리는 그 백엔드를 실제로 쓸 때만 import → 모델 없이도 화면 개발·테스트 가능

### `kiosk/gestures.py` — 탐지 결과를 명령으로 (핵심, 🅑 설명 필수)
1. **활성 손 선택** `select_active_hand()`: 신뢰도 0.5 이상 + 화면 면적 0.4% 이상 손 중 **가장 큰 손** = 키오스크에 가장 가까운 사용자. 뒤에서 지나가는 사람 손 무시
   - 같은 손에 **클래스만 다른 박스가 겹쳐** 나올 때가 있음 (예: palm 0.45 + like 0.44 — 손 모양이 바뀌는 순간에 특히). 탐지기의 NMS 는 보통 **같은 클래스끼리만** 겹친 박스를 지우기 때문
   - 그래서 가장 큰 손과 **IoU(겹친 넓이 ÷ 합친 넓이) ≥ 0.5** 인 박스들은 같은 손으로 보고, 그중 **신뢰도가 가장 높은 것**을 고름 → 라벨이 프레임마다 바뀌는 깜빡임 감소
2. **다수결 안정화** `_vote()`: 최근 5프레임 중 3번 이상 나온 제스처만 인정 → 1~2프레임 오분류(깜빡임) 제거
3. **커서** `_update_cursor()`:
   - 검지 끝은 박스 위쪽에 있으므로 박스 위 20% 지점을 포인터로
   - `active_region`(카메라 화면의 가운데 영역)을 화면 전체로 늘려서 팔을 크게 안 움직여도 화면 끝까지 닿게
   - **좌우 반전**: 셀피 카메라는 사용자가 오른쪽으로 움직이면 영상에서는 왼쪽으로 움직임 → `1 - x`
   - **EMA 평활화**: `새커서 = α·목표 + (1-α)·이전커서` (α=0.35) → 손 떨림 감소, 대신 약간 늦게 따라옴
4. **클릭**: 안정 제스처가 `one` 이었다가 0.8초 안에 `fist` 로 바뀌면. 주먹만 쥐고 있는 것은 클릭이 아님 (오클릭 방지). 화면 쪽에는 **dwell 클릭**(같은 버튼 1.5초 가리키기)도 있어 주먹 인식이 약해도 사용 가능
5. **스와이프** `_check_swipe()`: `palm` 손바닥 중심 좌표를 0.45초 동안 기록 → 가로 이동 ≥ 화면폭 18% 이고 세로 흔들림 ≤ 12% 이면 스와이프. 방향은 반전을 고려해 "사용자가 보는 화면 기준"
6. **유지형 명령** `_check_hold()`: like/dislike/peace 를 0.7초 유지하면 확인/뒤로/처음. 진행률을 `hold` 이벤트로 보내 화면에 게이지 → 사용자가 "곧 실행된다"를 알 수 있음
7. **쿨다운**: 명령 직후 0.9초 동안 새 명령 금지 → 한 번의 동작이 연속 실행되는 것 방지

> 모든 판정은 시간(t)을 인자로 받는 **순수 함수형 로직**이라 카메라 없이 가짜 탐지 결과로 테스트(`tests/test_gestures.py`)할 수 있습니다.

### `kiosk/engine.py` — 실시간 루프
- 별도 스레드에서 `카메라 읽기 → 탐지(시간 측정) → 해석 → 이벤트 콜백` 반복
- FPS·지연시간을 EMA 로 계산해 0.5초마다 `status` 이벤트
- 미리보기: 박스를 그리고 좌우 반전 후 JPEG 로 저장 → `/video` 가 MJPEG 로 스트리밍
- 명령 이벤트를 `logs/events_*.csv` 에 기록 → `eval_commands.py` 로 인식률 계산
- `--video 파일` 이면 웹캠 대신 영상을 **원래 속도(파일 FPS)대로** 재생. 제스처 판정(유지 0.7초, 스와이프 0.45초 등)이 시간 기준이라, 빨리 감으면 판정이 달라지기 때문

### `kiosk/server.py` — 웹 서버
- FastAPI: 화면 파일 제공, `/api/content`, `/api/status`, `/video`
- **WebSocket**: 서버가 먼저 화면에 이벤트를 밀어줄 수 있는 양방향 연결 (HTTP 요청-응답으로는 30fps 커서를 보내기 어려움)
- 엔진 스레드 ↔ asyncio 루프 사이는 `loop.call_soon_threadsafe` 로 안전하게 전달

### `web/app.js` — 화면
- 이벤트에 따라 커서 이동, `document.elementFromPoint()` 로 커서 아래 버튼 찾기(hover), 클릭·스와이프·확인 실행
- dwell 링: `requestAnimationFrame` 마다 hover 시간 / 1.5초 를 원형 게이지로
- 마우스·키보드로 같은 이벤트를 흉내 → 모델 없이 화면 개발 (mock 모드)
- 45초 입력 없으면 대기 화면으로 복귀 (실제 키오스크처럼)

### `training/` — 🅐 설명 필수
- `prepare_hagrid.py`: HaGRID JSON → YOLO txt(클래스 cx cy w h) + COCO json(RF-DETR 용). 클래스별 최대 장수 제한으로 학습 시간 조절
- `train_yolo.py`: 사전학습 가중치(COCO 로 학습된 yolo26n.pt)에서 **전이학습** → 손동작 6클래스로 미세조정
- `evaluate.py`: mAP(테스트셋) + 지연시간(같은 래퍼로 200장, 평균·p50·p95)
- `eval_commands.py`: 시나리오(기대 명령 순서)와 실제 로그를 `difflib` 로 정렬해 정확·누락·오인식·오발동을 셈
